# Telegram-бот как продукт: как проектировать сценарий, а не меню из кнопок

Telegram Bot API позволяет довольно быстро собрать интерфейс с командами, inline-кнопками и состояниями. Но техническая скорость легко создаёт другую проблему: бот начинает повторять структуру технического задания вместо реального пользовательского сценария.

Ниже — несколько принципов, которые я использую при проектировании прикладных Telegram-ботов.

## 1. Начинать с действия пользователя

Вместо списка экранов полезнее описать самое частое действие: что человек хочет сделать, какие данные для этого нужны и что система должна сделать после ввода.

Например, в финансовом планере ежедневное действие — занести расход. Если для этого нужно открыть четыре уровня меню, продуктом быстро перестают пользоваться.

## 2. Разделять интерфейс и бизнес-логику

Telegram — транспорт и UI. Расчёты, статусы, интеграции и правила лучше держать отдельным слоем. Тогда сценарий можно менять без переписывания всей системы, а те же данные при необходимости использовать в админке или веб-интерфейсе.

## 3. Не хранить состояние только в диалоге

Чат выглядит последовательным для пользователя, но события в реальной системе не всегда приходят последовательно. Оплаты, webhook-и, действия менеджеров и фоновые задачи требуют явной модели состояния.

## 4. Учитывать повторные действия

/start, повторное нажатие кнопки, возврат после паузы, дубль webhook — нормальные сценарии, а не исключения. Их лучше закладывать до запуска.

## 5. Проверять сценарий на коротком пути

Если основное действие можно сделать быстрее, чем объяснить его пользователю, интерфейс обычно получается устойчивее.
