# Как сделать публичный SEO-crawler и не превратить его в SSRF-прокси

Публичный сервис аудита сайта выглядит просто: пользователь вводит URL, backend скачивает страницу, разбирает HTML и показывает технические проблемы. Но в момент, когда сервер начинает ходить по адресу, который прислал пользователь, задача перестаёт быть только про SEO.

Появляется SSRF - возможность заставить сервер сделать запрос туда, куда обычный внешний пользователь попасть не должен.

Ниже - архитектура, которую я использовал в SiteAudit Studio для публичного crawler. Здесь нет попытки построить универсальный security framework. Цель уже: безопасно проверить публичный HTTP(S)-сайт, пройти ограниченное количество внутренних URL и не дать пользовательскому адресу превратить crawler в прокси к внутренней сети.

## Почему обычной проверки `http://` и `https://` недостаточно

Самый первый фильтр очевиден: принимать только HTTP и HTTPS.

Это отсекает `file://`, `ftp://` и другие схемы, но почти не решает SSRF. Опасный адрес всё равно может выглядеть как обычный HTTP URL:

```text
http://127.0.0.1/
http://localhost/
http://169.254.169.254/
http://10.0.0.5/
```

Если backend просто передаст такой URL в `fetch()` или HTTP-клиент, запрос уйдёт уже из инфраструктуры сервиса. Для атакующего это другой сетевой контекст: из него могут быть доступны localhost, private subnet, metadata endpoints или внутренние сервисы.

Поэтому правило должно быть не "URL начинается с https", а "каждый исходящий запрос разрешён только к проверенному публичному адресу".

## 1. Сначала разбираем URL как структуру

До DNS и сети URL нужно разобрать штатным parser, а не регулярным выражением.

Минимальные проверки:

- схема только `http:` или `https:`;
- hostname присутствует;
- username/password в URL лучше запрещать;
- порт либо стандартный, либо явно разрешён политикой сервиса;
- URL нормализуется до канонической формы перед дальнейшей обработкой.

Почему не regexp? Потому что URL имеет слишком много пограничных вариантов: IPv6, percent-encoding, punycode, нестандартное представление host, порт, credentials. Сетевую политику проще строить поверх уже разобранных компонентов.

## 2. Проверяем не только hostname, но и результат DNS

Запретить строку `localhost` мало.

Например, публичное доменное имя может резолвиться в приватный IP. Значит после проверки hostname нужно выполнить DNS lookup и проверить все полученные адреса.

Блокируются как минимум:

- loopback;
- private IPv4 ranges;
- link-local;
- unspecified addresses;
- multicast;
- приватные и link-local диапазоны IPv6;
- служебные адреса, которые не должны быть целью публичного crawler.

Ключевой принцип: решение "можно идти" принимается по фактическому IP, а не только по красивому доменному имени.

## 3. Почему после DNS-проверки нельзя просто снова вызвать обычный `fetch(url)`

Здесь появляется классическая проблема DNS rebinding / time-of-check vs time-of-use.

Сценарий:

1. сервис проверяет домен;
2. DNS возвращает публичный IP;
3. проверка проходит;
4. HTTP-клиент сам повторно резолвит тот же домен;
5. DNS уже возвращает приватный адрес;
6. запрос уходит внутрь сети.

То есть мы проверили один IP, а реально подключились к другому.

Поэтому в SiteAudit запрос закрепляется за уже проверенным IP. DNS lookup является частью решения о доступе, а не декоративной проверкой перед обычным запросом.

## 4. IP pinning без поломки Host и TLS

Если просто заменить домен на IP в URL, можно сломать виртуальный хостинг и HTTPS.

Допустим, пользователь ввёл:

```text
https://example.com/page
```

DNS дал:

```text
203.0.113.10
```

TCP-соединение можно открыть именно к проверенному IP, но HTTP и TLS всё равно должны знать исходный hostname.

Поэтому сохраняются:

- HTTP `Host: example.com`;
- TLS server name / SNI `example.com`.

Получается нужное сочетание:

- сетевое соединение идёт к уже проверенному публичному IP;
- сертификат проверяется для исходного домена;
- сервер виртуального хостинга получает правильный Host.

Именно это делает pinning пригодным для реальных HTTPS-сайтов.

## 5. Каждый redirect - новый пользовательский ввод

Одна из частых ошибок SSRF-защиты - хорошо проверить первый URL и автоматически разрешить redirects.

Но публичная страница может ответить:

```text
302 Location: http://127.0.0.1:3000/admin
```

Если HTTP-клиент следует redirect автоматически, первая проверка теряет смысл.

Поэтому redirect лучше обрабатывать вручную:

1. получить `Location`;
2. собрать следующий URL относительно текущего;
3. заново проверить схему;
4. заново выполнить DNS;
5. заново проверить IP;
6. только потом делать следующий запрос.

И так на каждом переходе.

Дополнительно нужен лимит количества redirect, иначе crawler легко загнать в цикл.

## 6. Ограничения важны не меньше SSRF-фильтра

Даже если crawler ходит только к публичным адресам, его всё ещё можно использовать для лишней нагрузки.

Поэтому публичный аудит должен иметь жёсткие границы.

В SiteAudit ограничиваются:

- timeout одного запроса;
- максимальный размер ответа;
- количество redirect;
- размер crawl sample;
- concurrency;
- частота запусков с одного IP.

Это защищает сразу от нескольких классов проблем: зависающих серверов, огромных ответов, бесконечных цепочек, попытки использовать сервис как массовый scanner и банального DoS через дорогие аудиты.

## 7. Crawler не обязан скачивать весь сайт

Для технического аудита обычно не нужен обход десятков тысяч страниц.

Полезнее получить ограниченную выборку:

- стартовая страница;
- ссылки того же host;
- небольшой набор внутренних URL;
- robots.txt;
- sitemap, если он обнаружен.

Так можно проверить структуру, broken links, meta, canonical, заголовки и часть accessibility/security сигналов, не превращая один пользовательский запрос в долгую фоновую индексацию сайта.

Ограниченный crawl ещё и проще объяснить пользователю: результат отражает проверенную выборку, а не делает вид, что сервис полностью просканировал весь домен.

## 8. Что проверять в HTML после безопасного fetch

Когда сетевой слой уже не пропускает опасные назначения, начинается обычная техническая часть аудита.

В моём случае проверяются, среди прочего:

- HTTP status и базовая indexability;
- title и meta description;
- H1;
- canonical;
- robots meta;
- lang и viewport;
- robots.txt;
- sitemap discovery;
- internal/external links;
- часть broken links;
- изображения без `alt`;
- базовые security headers.

Важно разделять две вещи: "страница доступна crawler" и "страница хороша для поиска". Безопасный fetch - это инфраструктурная предпосылка, а не SEO-оценка сама по себе.

## 9. Почему объяснимые проверки полезнее одной AI-оценки

Для такого сервиса я специально не строил основную оценку вокруг модели, которая выдаёт общий score без доказательства.

Если проблема техническая, пользователь должен видеть конкретный сигнал:

- какой status code получен;
- какой canonical найден;
- что написано в robots;
- какой header отсутствует;
- какая ссылка вернула ошибку.

Это проще проверять, тестировать и исправлять.

AI можно добавить позже как слой объяснения или приоритизации, но сетевые ограничения и технические факты не должны зависеть от ответа модели.

## 10. Минимальный pipeline публичного crawler

В упрощённом виде путь одного URL выглядит так:

```text
user URL
   |
parse + normalize
   |
allow http/https only
   |
DNS resolve
   |
reject private/service IPs
   |
pin request to checked IP
   |
preserve Host + TLS SNI
   |
HTTP response
   |
redirect?
   | yes
repeat full validation
   |
size/time limits
   |
HTML parse
   |
technical checks
   |
bounded internal crawl
```

Главное здесь не конкретная библиотека. Главное - чтобы безопасность стояла в самом сетевом пути и выполнялась на каждом запросе.

## 11. Какие ошибки я бы искал при ревью похожего сервиса

Если мне дают backend публичного URL-аудита, я в первую очередь ищу такие конструкции:

```js
await fetch(req.body.url)
```

без отдельной сетевой политики.

Дальше проверяю:

- можно ли передать localhost;
- блокируются ли private IPv4/IPv6;
- что происходит с DNS;
- не делает ли клиент второй lookup после проверки;
- проверяются ли redirects;
- ограничен ли размер ответа;
- есть ли timeout;
- ограничен ли crawl;
- можно ли запускать сотни аудитов подряд.

Если хотя бы redirect идёт мимо общей проверки, SSRF-защита уже неполная.

## 12. Что в этой архитектуре сознательно не решается

Такой сетевой слой не превращает приложение в универсальный vulnerability scanner.

Он не доказывает безопасность самого проверяемого сайта и не заменяет pentest. Его задача уже: безопасно получить публичный HTTP(S)-контент для технического анализа.

Точно так же SEO-аудит не должен обещать "вывести сайт в топ". Он показывает измеримые технические сигналы, которые можно проверить и исправить.

## Итог

Публичный crawler - это сетевой сервис, даже если снаружи он выглядит как форма "введите сайт".

Надёжная схема начинается не с HTML parser, а с контроля исходящего соединения:

- разобрать URL;
- разрешить только HTTP(S);
- проверить DNS и фактические IP;
- заблокировать приватные и служебные сети;
- закрепить запрос за проверенным IP;
- сохранить Host и TLS SNI;
- повторять полную проверку на каждом redirect;
- ограничить время, объём и глубину crawl.

После этого уже имеет смысл строить SEO, accessibility и security checks поверх полученного ответа.
