# Почему Telegram webhook стоит делать идемпотентным ещё до первого реального пользователя

У Telegram-бота может быть полностью рабочий интерфейс и при этом довольно хрупкая обработка событий. Это особенно незаметно на локальных тестах: нажал кнопку один раз — получил один callback, отправил сообщение — получил один update, webhook вернул 200 — всё выглядит предсказуемо.

Проблема появляется в тот момент, когда сеть перестаёт вести себя как идеальный провод.

Telegram Bot API повторяет webhook-запросы, если endpoint отвечает неуспешным HTTP-статусом. Это нормальный механизм доставки, но для приложения он означает простое правило: один и тот же бизнес-сценарий потенциально может быть запущен повторно.

Если обработчик только отправляет текст «Привет», ничего страшного. Если он создаёт заказ, начисляет баланс, выдаёт подписку, записывает оплату или отправляет заявку в CRM, повтор уже становится бизнес-ошибкой.

## HTTP-запрос и бизнес-операция — разные вещи

Представим типичный обработчик:

```python
async def webhook(update):
    await create_order(update)
    await send_confirmation(update)
    return Response(status_code=200)
```

Выглядит логично. Но теперь допустим, что `create_order()` успешно записал заказ, подтверждение тоже ушло, а соединение оборвалось раньше, чем Telegram получил HTTP 200.

Для Telegram запрос выглядит неуспешным. Он может быть доставлен снова.

Для нашей системы операция уже выполнена.

Второй вызов `create_order()` создаст дубль, если на уровне приложения нет дополнительной защиты.

То есть задача обработчика — не просто «не упасть». Он должен уметь безопасно встретить уже обработанное событие.

## update_id — удобная первая линия защиты

Каждый Telegram Update содержит `update_id`. Для многих сценариев его достаточно использовать как идентификатор входящего события.

Самая простая версия выглядит примерно так:

```python
async def process_update(update):
    if await processed_updates.exists(update.update_id):
        return

    await handle(update)
    await processed_updates.add(update.update_id)
```

Но у такого примера есть неприятное окно.

Если `handle(update)` успел изменить бизнес-состояние, а процесс упал до `processed_updates.add()`, при повторной доставке операция снова выполнится.

Если же сначала записать `update_id`, а потом выполнять действие, возможна обратная проблема: отметка уже есть, но само действие не завершилось.

Поэтому для критичных операций простого `exists()` недостаточно.

## Идемпотентность лучше привязывать к самой операции

Если update создаёт заявку, полезнее защищать не только входящий update, но и сущность, которую он создаёт.

Например, у заявки может быть уникальный `source_event_id`:

```sql
CREATE TABLE leads (
    id BIGSERIAL PRIMARY KEY,
    source_event_id BIGINT UNIQUE NOT NULL,
    telegram_user_id BIGINT NOT NULL,
    payload JSONB NOT NULL
);
```

Тогда повторная попытка вставить ту же заявку упрётся в уникальное ограничение БД.

Это важнее проверки в памяти приложения, потому что несколько процессов или экземпляров сервиса могут одновременно получить связанные события.

Похожий подход работает для платежей, заказов и фоновых задач: у бизнес-операции должен быть ключ, по которому система понимает, что она уже произошла.

## Что делать с транзакцией

Надёжная схема обычно требует объединить изменение состояния и фиксацию обработанного события в одну транзакцию.

Условный пример:

```python
async with db.transaction():
    inserted = await processed_updates.insert_if_absent(update.update_id)
    if not inserted:
        return

    await apply_business_change(update)
```

Если транзакция откатывается, откатываются обе части. Если фиксируется — и отметка, и бизнес-изменение становятся видимыми вместе.

Конкретная реализация зависит от базы и ORM, но смысл именно в отсутствии промежуточного состояния «операция уже выполнена, а событие ещё считается необработанным».

## А что с callback_query

Повторный webhook — не единственный источник дублей.

Пользователь сам может несколько раз нажать inline-кнопку. У интерфейса есть задержка, человек не видит мгновенной реакции и нажимает ещё раз.

Если кнопка означает «показать следующий экран», это почти безвредно. Если она означает «подтвердить заказ» или «списать бонусы», действие должно быть защищено уже на уровне бизнес-сущности.

Например, переход заказа из `draft` в `confirmed` можно сделать условным:

```sql
UPDATE orders
SET status = 'confirmed'
WHERE id = :id
  AND status = 'draft';
```

Если обновлена одна строка — переход произошёл. Если ноль — заказ либо уже подтверждён, либо находится в другом состоянии.

Такое поведение гораздо устойчивее, чем просто надеяться, что пользователь нажмёт кнопку ровно один раз.

## Повторная отправка сообщения — отдельная проблема

Даже если изменение данных идемпотентно, побочный эффект может выполниться повторно.

Например:

1. заказ подтверждён;
2. бот отправляет менеджеру уведомление;
3. процесс падает;
4. update приходит снова;
5. состояние заказа уже корректное, но уведомление отправляется повторно.

Для некритичного сообщения это терпимо. Для email, платежного действия или вызова внешнего API уже нет.

Здесь помогают несколько подходов: outbox-таблица, отдельная очередь задач или собственный идентификатор операции для внешнего сервиса, если он поддерживает idempotency key.

В простом приложении это может выглядеть избыточно, но как только бот становится частью рабочего процесса, побочные эффекты начинают требовать такой же аккуратности, как изменения в БД.

## Быстрый ответ webhook или обработка внутри запроса

Есть ещё один практический вопрос: сколько работы выполнять до HTTP 200.

Если обработчик делает длинный запрос в CRM, генерирует документ и отправляет несколько сообщений, время ответа растёт. Чем больше внешних зависимостей внутри webhook-request, тем больше мест, где запрос может завершиться ошибкой.

Часто удобнее быстро проверить входные данные, сохранить update и передать тяжёлую обработку в очередь:

```python
async def webhook(update):
    saved = await inbox.save_if_absent(update)
    if saved:
        await queue.publish(update.update_id)
    return Response(status_code=200)
```

Worker уже выполняет бизнес-операцию отдельно.

У такого подхода свои сложности: очередь тоже требует подтверждений, retries и контроля дублей. Но HTTP-доставка Telegram перестаёт быть одновременно и транспортом, и жизненным циклом всей бизнес-операции.

## Не забывать про наблюдаемость

Telegram предоставляет `getWebhookInfo`, где среди прочего можно увидеть количество ожидающих updates и информацию о последних ошибках доставки.

Но для реального проекта полезно логировать ещё как минимум:

- `update_id`;
- тип update;
- время обработки;
- результат бизнес-операции;
- повторность события;
- ошибку внешней интеграции.

Тогда ситуация «бот иногда дублирует заявки» превращается из гадания в конкретную последовательность событий.

## Минимальный практический чек-лист

Перед запуском webhook-бота я бы проверил несколько вещей.

Один и тот же update можно отправить endpoint дважды — состояние системы не меняется второй раз.

Одну и ту же inline-кнопку можно нажать несколько раз — критичное действие выполняется один раз.

Падение процесса между изменением данных и ответом webhook не создаёт дубль после повторной доставки.

Временная ошибка CRM или другого API не теряет пользовательские данные.

Повторная задача из очереди не повторяет необратимый побочный эффект.

Есть способ понять по логам, какой update создал конкретную запись.

## Итог

Telegram Bot API сам по себе довольно простой. Большинство неприятных ошибок появляется не на уровне метода `sendMessage`, а на границе между доставкой события и бизнес-операцией.

Webhook — это уведомление о событии, а не гарантия, что оно придёт ровно один раз в идеальный момент.

Если относиться к повторной доставке как к нормальной части системы с самого начала, бот гораздо спокойнее переживает сетевые ошибки, рестарты и рост нагрузки. Идемпотентность в этом смысле — не «архитектура для больших проектов», а довольно дешёвая страховка от очень неприятных дублей.
